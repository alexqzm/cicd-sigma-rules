# Источники событий и допущения о полях

## Журнал аудита GitHub (`product: github`, `service: audit`)

Где взять события:

- **потоковая передача журнала аудита** предприятия (GitHub Enterprise Cloud и Server) в
  SIEM или хранилище;
- **REST API журнала аудита** — для организаций GitHub Enterprise Cloud;
- **выгрузка JSON/CSV** из настроек организации.

События `workflows.created_workflow_run` и `workflows.prepared_workflow_job` в веб-интерфейсе
не показываются — только через REST API, потоковую передачу и выгрузки (по документации GitHub).

Имена событий и полей в правилах — из документации GitHub, как в правилах SigmaHQ для того же
источника. Каталог [`data/github-audit-events.json`](../data/github-audit-events.json) хранит
события, на которые ссылаются правила и эталонные события, с полями из документации
(`github/docs`, `src/audit-logs/data`, коммит `8cd1075`, 06.11.2026). Тест
`tests/test_catalog.py` проверяет, что правила и эталонные события используют только
задокументированные события и только поля, документированные для этих событий. Обновить
каталог: `python -m tools.catalog sync <клон github/docs>`.

### Допущения о значениях

Документация называет поля, но не описывает их значения. Правила опираются на такие допущения;
проверьте их на своих данных.

| Поле | Событие | Допущение | Правила |
|---|---|---|---|
| `event` | `workflows.created_workflow_run` | имя события-триггера, как в ключе `on:` рабочего процесса: `pull_request_target`, `workflow_dispatch` | запуски по `pull_request_target`, корреляция |
| `public_repo` | `workflows.created_workflow_run`, `repo.register_self_hosted_runner` | логическое `true` для публичного репозитория | запуски по `pull_request_target`, исполнитель в публичном репозитории |
| `runner_group_allow_public` | `org.runner_group_created`, `org.runner_group_updated` | логическое значение текущей настройки группы | группа исполнителей открыта публичным репозиториям |
| `repo` | все | полное имя `организация/репозиторий` (пример в документации — `octo-org/documentation`) | группировка корреляции |
| `@timestamp` | все | время события в миллисекундах от эпохи, как `created_at` в примере выгрузки из документации | окно корреляции |

В эталонных событиях логические поля — логические значения JSON; если в вашей SIEM они
хранятся строками, проверьте запросы на своих данных (этот случай не проверялся).

В примере ключей выгрузки из документации часть полей события идёт с префиксом `data.`
(`data.email`, `data.hook_id`). Если ваш источник так вкладывает поля, переименуйте их
конвейером pySigma.

Правила, которые срабатывают на любое изменение политики (`*_policy_changed`), не смотрят на
новое значение, потому что формат значений полей политики (`policy`, `new_policy`,
`default_workflow_permissions_value` и др.) не задокументирован. После того как формат известен
по своим данным, правило можно сузить до ослабления политики.

## Создание процессов в Linux (`product: linux`, `category: process_creation`)

Поля — из таксономии Sigma для `process_creation`: `Image`, `CommandLine`, `ParentImage`,
`ParentCommandLine`, `CurrentDirectory`, `User`, `ProcessId`, `ParentProcessId`. Их дают Sysmon
for Linux, auditd с соответствующим конвейером полей или EDR. Правила рассчитаны прежде всего
на собственные исполнители, сборочные серверы и рабочие станции разработчиков; для
исполнителей, размещённых GitHub, такую телеметрию нужно собирать отдельно.

Правило поиска маркеров секретов опирается на подстроку `isSecret` в командной строке. Регистр
в Sigma не учитывается, но в SIEM — зависит от хранения поля (см. [`siem.md`](siem.md)).

## Эталонные события

`tests/events/<правило>/match.jsonl` и `nomatch.jsonl` — синтетические события, по одному в
строке, с полем `_test` (описание случая), которое в журнал не попадает. Они содержат только
поля из каталога (GitHub) или из списка выше (Linux), значения — вымышленные
(`example-org/...`, `example.invalid`), без данных реальных организаций. Это проверка логики
правил и конвертации, а не оценка частоты ложных срабатываний на реальных журналах.
